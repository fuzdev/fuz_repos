publishing_plan.ts

The publishing plan: what a release of the configured packages publishes, in what versions, and the dependency rewrites that go with it.

generate_publishing_plan resolves the whole cascade in one pass over the prod/peer topological order — explicit changesets, bump escalations a breaking dependency forces, and auto-generated changesets for dependents — then groups the packages that publish into waves: a wave's packages don't depend on each other, so they publish together.

The plan reads each package as its checkout sits. Given what the registry shows (GeneratePlanOptions.registry), it also accounts for releases already made: a package whose current version is out counts as released, and a dependent whose range still trails it gets the rewrite it missed.

generate_publishing_plan

publishing_plan.ts view source

(all_repos: LocalRepo[], options?: GeneratePlanOptions): Promise<PublishingPlan> import {generate_publishing_plan} from '@fuzdev/fuz_repos/publishing_plan.js';

Generates the publishing plan in one pass over the prod/peer topological order. Each package's dependencies are settled before it is reached, so its required bump — from its prod/peer ranges against each dependency's version after the release — is final when computed: explicit changesets, escalation, or an auto-changeset, with no iteration.

Every package's version after the release is its predicted one when it publishes and its current one otherwise, so a dependent whose range trails a dependency's current version gets that rewrite too, along with the bump it implies.

Packages whose current version the registry doesn't show, with no changesets: just published and still propagating, or a publish that failed. A package the registry has never seen is here too when another configured package has a prod/peer range on it — a first publish npm answers E404 for until it shows. Empty without registry observations.

never_published

Packages the registry has never seen, with no changesets of their own and no configured package depending on them for prod or peer — apps or sites that never publish, most likely, which private would say. Like private packages they're update-only leaves: no auto-bump, and no range moves for them. Empty without registry observations.
